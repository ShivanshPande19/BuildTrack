# Native setup (camera, photos, deep links)

`app/android/`, `app/ios/` and `app/web/` are generated by `flutter create .` and **are tracked in
this repo**, so a fresh clone builds without re-doing any of the setup below. Nothing here touches
`lib/` or `pubspec.yaml`.

Read this to understand *why* a permission or a version floor is there — **not** as a checklist to
apply. Everything below is committed.

> ### It was not always
>
> The platform folders were untracked until this pass, and when they were finally added they turned
> out to be **stock `flutter create` output**: no `CAMERA` permission, no deep-link intent filter, no
> iOS usage strings, `platform :ios, '13.0'` still commented out. This document described
> configuration that had never actually been applied to the project — it read like a record and
> behaved like a wish list.
>
> On a device that meant: the barcode scanner and every camera screen failed (only *Enter serial
> manually* survived), a release build could not reach Supabase at all, invite and password-recovery
> links could not hand the session back to the app, and iOS would have been rejected at review.
>
> If you ever regenerate the platform folders, `git diff` before committing — that is what would have
> caught this.

Two things stay out of the repo on purpose (see `.gitignore`):

- **`app/android/key.properties` and any `.jks` / `.keystore`** — release signing. A leaked keystore
  lets anyone ship an update that Android accepts as genuinely from Azimuth. These live on the
  release machine only.
- **Generated output** — `app/ios/Pods/`, `Flutter/Generated.xcconfig`, `.gradle/`,
  `local.properties`, etc. `flutter pub get` and `pod install` recreate them.

`pubspec.lock` and `ios/Podfile.lock` **are** committed, so every machine and CI resolve the same
dependency versions.

`ios/Podfile.lock` had gone stale in the same way: it listed `app_links`, `file_picker`,
`shared_preferences_foundation`, `url_launcher_ios` and `webview_flutter_wkwebview` but **neither
`mobile_scanner` nor `image_picker_ios`** — it predated both packages, so no iOS build had ever
included the barcode scanner or the camera. Regenerated with `pod install`.

**Re-run `pod install` whenever `Podfile` or `pubspec.yaml` changes**, and commit the result:

```sh
cd app && flutter pub get && cd ios && pod install
```

`Podfile.lock` records a `PODFILE CHECKSUM`, so a Podfile edit alone makes it stale even when the
resolved pods are identical.

Deep links for member invites are also described in [`INVITE_FLOW.md`](INVITE_FLOW.md) §3–4; both
edits are applied in this repo.

## Known warnings you can ignore

`pod install` prints this, and it is **not** a problem to chase:

```
[!] CocoaPods did not set the base configuration of your project because your project
    already has a custom config set. … please either set the base configurations of the
    target `Runner` to `Pods-Runner.profile.xcconfig` or include it in `Flutter/Release.xcconfig`
```

Flutter's iOS template ships only `Flutter/Debug.xcconfig` and `Flutter/Release.xcconfig`, and points
the Xcode **Profile** configuration at `Release.xcconfig`. That file `#include?`s
`Pods-Runner.release.xcconfig`, so CocoaPods notices its `Pods-Runner.profile.xcconfig` is unused and
says so. Debug and Release — the two that ship — are wired correctly, and profile builds fall back to
the release pod settings, which for these pods are equivalent.

It reproduces on a fresh `flutter create`, and Flutter tracks it as a misleading message rather than a
defect: [flutter#73845](https://github.com/flutter/flutter/issues/73845),
[flutter#66222](https://github.com/flutter/flutter/issues/66222). Fixing it properly means adding a
`Flutter/Profile.xcconfig` and re-pointing the build configuration in `project.pbxproj` — a
divergence from the template that Flutter upgrades will keep fighting, for no shipping benefit.

The other one, `Automatically assigning platform iOS with version 13.0 … because no platform was
specified`, meant the Podfile's `platform` line was still commented out. That is fixed; if you see it
again, the line got lost.

## Why these are needed

| Feature | Package | Needs |
|---|---|---|
| Workshop site photos · client ticket photos | `image_picker` | camera + photo library access |
| Scan a part's QR/barcode to install it | `mobile_scanner` | camera access |

Minimums the packages themselves require: **Android `minSdk` 23**, **iOS 13** (`image_picker_ios`
needs 13.0; `mobile_scanner` itself allows 12.0, so 13 covers both).

---

## 1. Android — `android/app/src/main/AndroidManifest.xml`

Add above `<application>`:

```xml
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.INTERNET" />
```

`INTERNET` is added automatically for debug builds but **not** for release — without it a release
build cannot reach Supabase at all.

Gallery picking needs no permission on modern Android: `image_picker` uses the system photo picker.

### `android/app/build.gradle.kts`

`mobile_scanner` requires `minSdk` 23. Recent Flutter templates already default higher, but if yours
is pinned lower, raise it:

```kotlin
defaultConfig {
    minSdk = 23
}
```

---

## 2. iOS — `ios/Runner/Info.plist`

Add inside the top-level `<dict>`. iOS **rejects the app at review** without a usage string, and the
permission prompt shows this text, so make it specific:

```xml
<key>NSCameraUsageDescription</key>
<string>BuildTrack uses the camera to scan part barcodes and take build photos.</string>

<key>NSPhotoLibraryUsageDescription</key>
<string>BuildTrack lets you attach photos of your build or of an issue you are reporting.</string>
```

### `ios/Podfile`

Ensure the platform is at least 13:

```ruby
platform :ios, '13.0'
```

Then `cd ios && pod install`.

---

## 3. Web (optional)

Both packages work on web, but the camera only works over **HTTPS** (or `localhost`). On plain HTTP
the browser blocks `getUserMedia` and the scanner shows its "camera not available" state.

## Verifying it works

1. **Workshop → a task → Photo** — the camera/gallery sheet appears, the photo previews, and after
   upload it shows on the client's stage timeline (it is a real file in the `builds` bucket now, not
   a `picsum.photos` placeholder).
2. **Workshop → scan button → Scan serial** — the viewfinder opens with a torch toggle. Scanning a
   part's label finds it by serial; **Enter serial manually** is the fallback for a damaged label.
3. **Client → Raise a request → Add a photo** — attaches to the ticket, and Service sees it under
   *Photos from the client* on the ticket.

If the camera screen shows "Camera not available", the permission was denied or the usage string is
missing — the manual-entry path still works.

## Storage

Photos go to the public **`builds`** bucket, created by
[`supabase/migrations/0011_builds_storage.sql`](../supabase/migrations/0011_builds_storage.sql):

- staff write anywhere in the bucket (`stages/<stageId>/…`)
- a client may only write under `tickets/…`
- public read, so the app loads them straight from the stored URL
